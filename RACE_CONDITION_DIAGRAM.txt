PROBLEM: Two admins updating quotas simultaneously can cause data loss

───────────────────────────────────────────────────────────────────────────
❌ CURRENT CODE (VULNERABLE TO RACE CONDITIONS)
───────────────────────────────────────────────────────────────────────────

Timeline of Events:

Time    Admin A                          Admin B
────────────────────────────────────────────────────────────────────────────
T1      Read org (max_devices=10)        
T2                                        Read org (max_devices=10)
T3      Modify: max_devices=50           
T4                                        Modify: max_users=25
T5      Commit (max_devices=50)          
T6                                        Commit (max_users=25)

Result: ❌ Admin A's change LOST! (max_devices reverted to 10)

Database State:
  T1: { max_devices: 10, max_users: 5 }
  T5: { max_devices: 50, max_users: 5 }  ← Admin A committed
  T6: { max_devices: 10, max_users: 25 } ← Admin B overwrites A's change!

Code Flow (PROBLEMATIC):
┌─────────────────────────────────────────────────────────────────────┐
│ Admin A Thread                  │ Admin B Thread                    │
├─────────────────────────────────┼───────────────────────────────────┤
│ 1. SELECT * FROM orgs WHERE ... │ 1. SELECT * FROM orgs WHERE ...   │
│    → { max_devices: 10 }        │    → { max_devices: 10 }          │
│                                 │                                   │
│ 2. org.max_devices = 50         │ 2. org.max_users = 25             │
│                                 │                                   │
│ 3. UPDATE orgs SET              │ 3. UPDATE orgs SET                │
│    max_devices=50               │    max_users=25                   │
│                                 │    max_devices=10 (unchanged!)    │
│                                 │                                   │
│ 4. COMMIT                       │ 4. COMMIT (overwrites A!)         │
└─────────────────────────────────┴───────────────────────────────────┘

✅ FIXED CODE (ATOMIC WITH ROW-LEVEL LOCKING)
───────────────────────────────────────────────────────────────────────────

Timeline of Events:

Time    Admin A                          Admin B
────────────────────────────────────────────────────────────────────────────
T1      Read org + LOCK (max_devices=10) 
T2                                        Wait for lock... ⏳
T3      Modify: max_devices=50           
T4                                        Still waiting... ⏳
T5      Commit (max_devices=50)          
T6      LOCK RELEASED ✓                  
T7                                        Read org + LOCK (max_devices=50)
T8                                        Modify: max_users=25
T9                                        Commit (max_users=25)
T10                                       LOCK RELEASED ✓

Result: ✅ Both changes preserved! (max_devices=50, max_users=25)

Database State:
  T1: { max_devices: 10, max_users: 5 }
  T5: { max_devices: 50, max_users: 5 }  ← Admin A committed
  T9: { max_devices: 50, max_users: 25 } ← Admin B sees A's change ✓

───────────────────────────────────────────────────────────────────────────
🔍 HOW ROW-LEVEL LOCKING WORKS
───────────────────────────────────────────────────────────────────────────

SELECT ... FOR UPDATE tells PostgreSQL:
  "I need exclusive access to this row until I commit my transaction"

Lock Behavior:
  ┌──────────────────────────────────────────────────────────────┐
  │ Transaction A                                                │
  ├──────────────────────────────────────────────────────────────┤
  │ BEGIN;                                                       │
  │ SELECT * FROM organizations WHERE id=1 FOR UPDATE;           │
  │ ┌────────────────────────────────────────────────┐           │
  │ │ 🔒 ROW LOCKED (id=1)                           │           │
  │ │                                                │           │
  │ │ Other transactions trying to access this row: │           │
  │ │   - Regular SELECT: ✅ Can read                │           │
  │ │   - SELECT FOR UPDATE: ⏳ Must wait            │           │
  │ │   - UPDATE: ⏳ Must wait                       │           │
  │ │   - DELETE: ⏳ Must wait                       │           │
  │ └────────────────────────────────────────────────┘           │
  │ UPDATE organizations SET max_devices=50 WHERE id=1;          │
  │ COMMIT;                                                      │
  │ 🔓 LOCK RELEASED - other transactions can now proceed       │
  └──────────────────────────────────────────────────────────────┘

📊 CODE COMPARISON
───────────────────────────────────────────────────────────────────────────

BEFORE (Vulnerable):
┌──────────────────────────────────────────────────────────────────────┐
│ def update_organization_quota(org_id, ...):                          │
│     org = db.query(OrganizationModel).filter(                        │
│         OrganizationModel.id == org_id                               │
│     ).first()  # ❌ No lock - race condition possible                │
│                                                                      │
│     if request_body.max_devices is not None:                         │
│         org.max_devices = request_body.max_devices                   │
│                                                                      │
│     db.commit()  # ❌ May overwrite concurrent changes               │
└──────────────────────────────────────────────────────────────────────┘

AFTER (Safe):
┌──────────────────────────────────────────────────────────────────────┐
│ def update_organization_quota(org_id, ...):                          │
│     try:                                                             │
│         org = db.query(OrganizationModel).filter(                    │
│             OrganizationModel.id == org_id                           │
│         ).with_for_update().first()  # ✅ Acquires row lock          │
│                                                                      │
│         if not org:                                                  │
│             raise HTTPException(404, "Organization not found")       │
│                                                                      │
│         if request_body.max_devices is not None:                     │
│             org.max_devices = request_body.max_devices               │
│                                                                      │
│         db.commit()  # ✅ Atomic - no concurrent overwrites          │
│         db.refresh(org)                                              │
│                                                                      │
│     except Exception as e:                                           │
│         db.rollback()  # ✅ Rollback on error                        │
│         raise                                                        │
└──────────────────────────────────────────────────────────────────────┘

🎯 REAL-WORLD SCENARIO
───────────────────────────────────────────────────────────────────────────

Scenario: Two admins managing Hotel ABC's quotas

WITHOUT FIX:
  Admin Sarah: "Let's increase device limit to 50 for new TVs"
  Admin John:  "We need more users, let's set limit to 30"
  
  Result after both update:
    ❌ Device limit: 10 (Sarah's change LOST!)
    ✅ User limit: 30 (John's change OK)
  
  Sarah's change silently disappeared! 😱

WITH FIX:
  Admin Sarah: "Let's increase device limit to 50 for new TVs"
               → Updates quota, transaction commits
  Admin John:  "We need more users, let's set limit to 30"
               → Waits for Sarah's transaction to complete
               → Reads updated state (device_limit=50)
               → Updates user limit, preserves device limit
  
  Result after both update:
    ✅ Device limit: 50 (Sarah's change preserved!)
    ✅ User limit: 30 (John's change preserved!)
  
  Both changes applied correctly! 🎉
