# Device Implementation - Quick Reference

## Core Tables & Relationships

```
devices (main registry)
├─ device_tags (M:N) ──── tags
├─ playlist_assignments ── playlists ──── playlist_content ──── contents
├─ content_assignments ─── contents
├─ device_commands (1:N)
├─ device_logs (1:N)
├─ device_speed_tests (1:N)
└─ created_by ──────────── users

All devices belong to: organizations (multi-tenant)
```

## Device Status Flow

```
DEVICE LIFECYCLE:

pending  ──────> active  ──────> inactive
  ↑               │                 │
  │         (heartbeat)             │ (after release/reset)
  │         (content fetch)         │
  │         (commands)              │
  │                                 │
  └─────────── new code ───────────┘

maintenance (admin pause state)
```

## Device Commands

```
reset       ─ Clear localStorage + IndexedDB + reload
refresh     ─ Clear content cache only
reload      ─ Reload player
run_speed_test ─ Execute network speed test

Status: pending ──> executed OR expired (7-day auto-expire)
```

## Device Authentication

```
REGISTRATION
  │
  └─> Viewer calls POST /devices/monitor/register
      ├─ organization_pin: required (for org identification)
      ├─ activation_code: 6-digit code generated by device
      ├─ device_type: auto-detected (tv/monitor based on platform)
      └─ Response: { device_id, status: "pending" }

ACTIVATION
  │
  └─> Admin approves in Web UI
      │
      └─> Device polls GET /check-activation/{code}
          └─> Response: { activated: true, device_token: "jwt..." }

USAGE
  │
  └─> Device sends Authorization: Bearer <jwt_token>
      ├─ POST /heartbeat (every 30-60 sec)
      ├─ GET /commands/pending
      └─ GET /content/device/{id}

TOKEN REFRESH
  │
  └─> Before expiry (30 days), call POST /devices/refresh
      └─> Response: { token: "new_jwt", token_expires_at: "..." }
```

## Content Resolution Algorithm

```
Device requests content at preview_time:

1. Check device.status == "active" (else return empty)

2. Determine mode:
   ├─ EXCLUSIVE: Any exclusive playlist assigned?
   │             → Use ONLY playlist content
   │
   └─ INCLUSIVE: Merge all sources by priority
      ├─ Direct assignments (device_id set)
      │  └─ Sort: priority DESC, display_order ASC
      │
      ├─ Tag assignments (device has tags)
      │  └─ Sort: tag_priority DESC, then content priority
      │
      └─ Playlist content (playlist assigned to device/tag)
         └─ Sort: playlist.priority DESC
         └─ Check: playlist scheduling (start_time, end_time, days)
         └─ Check: content scheduling (start_date, end_date)

3. Filter:
   └─ is_active == true (soft delete)
   └─ within scheduling window if defined
   └─ exclude inactive sources

4. Return: Ordered list of content_ids to display
```

## Device Tags

```
Tags used to:
  1. Group devices by category (e.g., "Floor 1", "Premium Displays")
  2. Assign content to groups instead of individual devices
  3. Control priority (tag_priority field)

Device can have multiple tags:
  Device 1 ──── device_tags ──── Tag "Floor 1"
                                  Tag "Premium"
                                  Tag "Lobby"

Content can be assigned to tags:
  Content 1 ──── content_assignments ──── Tag "Floor 1"
                                          (plays on all devices with tag)
```

## Multi-Tenancy

```
Organization PIN Registration:
  Viewer: POST /devices/monitor/register
  {
    "organization_pin": "12345678",
    "activation_code": "123456",
    ...
  }
  └─> Backend: Find org by PIN, assign device to org

Query Filtering:
  User has organization_id → All queries filtered to that org
  Example: GET /devices → Only devices in user's org
  
Cross-org Access:
  Device from Org A + User from Org B
  → GET /devices/{org_a_device_id} returns 404 (not found)
```

## Online/Offline Detection

```
Device online    ← last_seen < 5 minutes (heartbeat fresh)
Device offline   ← last_seen > 5 minutes (no recent heartbeat)
Device pending   ← never seen (status = "pending")

Automatic online detection:
  Device sends POST /heartbeat regularly
  └─> Updates last_seen = now()
  └─> Web UI shows "Online" if last_seen < 5 min
```

## Security Features

1. **JWT Authentication**
   - 30-day token expiry
   - Refresh at < 7 days remaining
   - Type check: "device" vs "user"
   - Signature verification

2. **Activation Code Security**
   - 6-digit alphanumeric (excludes O, I, 0, 1)
   - 10-minute expiration
   - Unique per system
   - Tied to organization PIN

3. **Status-Based Access**
   - Only active devices can access content
   - Pending devices cannot authenticate
   - Inactive devices blocked from API

4. **Command Expiration**
   - Auto-expire after 7 days
   - Prevents stale command execution

5. **Organization Isolation**
   - All queries filtered by org_id
   - Cross-org access returns 404

## Common Workflows

### Activate New Device
```
1. Device boots → POST /devices/monitor/register (with org PIN)
2. Display activation code on screen
3. Admin views pending device in Web UI
4. Admin clicks "Approve"
5. Device polls GET /check-activation/{code} detects activation
6. Device receives JWT token from response
7. Device stores token locally
8. Device ready to receive content
```

### Release Device
```
1. Admin clicks "Release" in Web UI
2. Backend queues RESET command
3. Backend sets status = "inactive"
4. Backend clears unique_code
5. Device detects RESET command
6. Device executes: localStorage.clear() + indexedDB.delete() + reload
7. Device re-registers as NEW pending device
```

### Assign Content to Device
```
1. Admin selects device in Web UI
2. Admin selects content to assign
3. POST /devices/{device_id}/content
4. Device fetches content on next heartbeat
5. Player displays content in rotation
```

### Assign Content to Tag
```
1. Admin creates tag "Floor 1"
2. Admin assigns devices to tag
3. Admin assigns content to tag
4. All devices with "Floor 1" tag receive content
5. Content plays on all tagged devices
```

### Remote Command Execution
```
1. Admin queues command (e.g., "reset")
2. Device polls GET /devices/{id}/commands/pending
3. Device receives pending commands
4. Device executes command (e.g., localStorage.clear())
5. Device confirms: POST /devices/{id}/commands/{cmd_id}/execute
6. Command status: pending → executed
```

## Error Codes

| Code | Scenario |
|------|----------|
| 201 | Device registered/activated successfully |
| 204 | Device deleted or content unassigned |
| 400 | Invalid request (e.g., code expired, device not active) |
| 401 | Authentication failed (invalid token) |
| 403 | Device inactive or insufficient permissions |
| 404 | Device/content not found or org mismatch |
| 409 | Conflict (e.g., code already exists, assignment exists) |
| 410 | Resource gone (activation code expired) |
| 500 | Server error (e.g., command queueing failed) |
