ARCHITECTURE FINDINGS
=====================

DEVICE TYPES: 2
├─ TV (WebOS/native)
│  ├─ Registration: POST /devices/tv (admin or system)
│  ├─ Status: Immediately active upon creation
│  ├─ Auth: IP + passphrase (legacy) or JWT (new)
│  └─ Special fields: ip_address, passphrase, platform, firmware_version
│
└─ Monitor (browser-based)
   ├─ Registration: POST /devices/monitor/register (self-registration)
   ├─ Status: Starts pending, requires admin approval
   ├─ Auth: 6-digit activation code → JWT token
   └─ Special fields: unique_code, code_expires_at

DEVICE STATUS LIFECYCLE: 4 states + 1 special
├─ pending (not yet approved, code expires in 10 min)
├─ active (fully operational, can fetch content)
├─ inactive (released/orphaned, can receive commands)
├─ maintenance (admin pause, not in normal flow)
└─ deleted (cascades all relationships, no recovery)

DATABASE TABLES: 7 (device-related)
├─ devices (core, 42 columns tracking identification, hardware, status)
├─ device_tags (N:M junction, group devices by category)
├─ device_logs (remote debugging, console logs from viewer)
├─ device_commands (remote instruction queue, reset/refresh/reload/speed_test)
├─ device_speed_tests (network monitoring, last 100 per device)
├─ playlist_assignments (assign playlists to device or tags)
└─ content_assignments (assign content to device or tags)

API ENDPOINTS: 21
├─ Device Registration/Activation (5 endpoints)
├─ Device Management (6 endpoints)
├─ Device Heartbeat & Commands (6 endpoints)
├─ Content Assignment (3 endpoints)
├─ Device Preview (1 endpoint)
└─ Device Authentication (1 endpoint)

AUTHENTICATION: JWT-based
├─ Token validity: 30 days
├─ Refresh threshold: < 7 days remaining
├─ Type check: "device" token vs "user" token
├─ Verification: Signature check + device.status == "active"
├─ Backward compatibility: ?device_id query param (deprecated)
└─ Auto-update last_seen on each authentication

CONTENT ROUTING: 3-tier priority system
├─ Direct assignments (device_id set)
├─ Tag-based assignments (device has tags)
└─ Playlist-based (playlist assigned to device/tag)
With exclusive vs inclusive mode support and scheduling

MULTI-TENANCY: Organization isolation
├─ All device queries auto-filtered by organization_id
├─ Device registration tied to PIN (for viewer self-registration)
├─ Cross-org access returns 404 (not found)
└─ 8-digit PIN used to determine target organization

REMOTE MANAGEMENT: Command queue system
├─ Admin queues commands (reset, refresh, reload, speed_test)
├─ Device polls /commands/pending during heartbeat
├─ Device executes command locally (e.g., localStorage.clear())
├─ Device confirms execution with /commands/{id}/execute
├─ Command auto-expires after 7 days if not executed
└─ Enable remote troubleshooting without physical access

ONLINE/OFFLINE DETECTION: Heartbeat-based
├─ Device sends heartbeat every 30-60 seconds
├─ Backend updates last_seen timestamp
├─ UI threshold: last_seen < 5 minutes = online
├─ UI threshold: last_seen > 5 minutes = offline
└─ Used for connection health monitoring

NETWORK MONITORING: Speed test integration
├─ Device polls for speed_test command
├─ Records: download, upload, latency, jitter, packet_loss
├─ Quality classification: good (DL >= 25, UL >= 10), fair, poor
├─ Last 100 tests kept per device (auto-cleanup)
└─ Helps diagnose network issues remotely

KEY BUSINESS LOGIC
==================

1. DEVICE REGISTRATION FLOW
   Viewer → POST /devices/monitor/register (no auth)
   Backend: Validate org PIN, create device, status="pending"
   Viewer: Display activation code on screen
   Admin: Views pending device in Web UI
   Admin: Clicks approve (PUT /devices/{id}, status="active")
   Viewer: Polls /check-activation/{code}
   Viewer: Receives JWT token in response
   Viewer: Uses token for all subsequent API calls

2. CONTENT DELIVERY FLOW
   Device: POST /heartbeat (Bearer token)
   Backend: Update last_seen, check for commands
   Backend: Response includes rotation, volume_enabled
   Device: GET /commands/pending
   Device: Execute commands (e.g., localStorage.clear())
   Device: GET /content/device/{id}
   Backend: Apply content resolution algorithm:
     - Check device.status == "active"
     - Merge: direct + tag + playlist assignments
     - Apply priority and scheduling
     - Return ordered content list
   Device: Display content in rotation

3. RELEASE DEVICE FLOW (without deletion)
   Admin: POST /devices/{id}/release
   Backend: Queue RESET command
   Backend: Set status="inactive", clear unique_code
   Backend: Keep device record and assignments for re-activation
   Device: Receives RESET command
   Device: Clears localStorage + indexedDB + reloads
   Device: Shows activation screen, generates new code
   Device: Re-registers as NEW pending device

4. DELETE DEVICE FLOW (permanent)
   Admin: DELETE /devices/{id}
   Backend: Queue RESET command (grace period)
   Backend: CASCADE delete all relationships:
     - device_tags (all tag assignments)
     - content_assignments
     - playlist_assignments
     - device_logs
     - device_commands
     - device_speed_tests
   Backend: Delete device record (NO RECOVERY)
   Result: Complete removal from system

SECURITY IMPLEMENTATION
=======================

1. Device Authentication
   ✓ JWT tokens with signature verification
   ✓ 30-day expiration (auto-refresh at < 7 days)
   ✓ Type field to distinguish device vs user tokens
   ✓ Device must be active to use token
   ✓ Backward compatibility with deprecated ?device_id param

2. Activation Code Security
   ✓ 6-digit alphanumeric (excludes O, I, 0, 1 to prevent confusion)
   ✓ 10-minute expiration (auto-cleanup of stale codes)
   ✓ Unique constraint per system (cannot reuse codes)
   ✓ Tied to organization PIN (org-level isolation)
   ✓ No auth required for /register endpoint (for viewer clients)

3. Organization Isolation
   ✓ All device queries filtered by organization_id
   ✓ Cross-org access returns 404 (not 403, hides existence)
   ✓ Device registration validates org PIN
   ✓ User's org determines accessible devices
   ✓ Device cannot see other org's content/tags/playlists

4. Status-Based Access Control
   ✓ Only active devices can authenticate
   ✓ Only active devices can fetch content
   ✓ Inactive devices cannot make API calls
   ✓ Pending devices blocked (must be approved first)
   ✓ Maintenance status prevents content delivery

5. Command Expiration
   ✓ Commands auto-expire after 7 days
   ✓ Device cannot execute expired commands
   ✓ Prevents unintended execution of stale commands
   ✓ Visible in device logs for audit trail

PERFORMANCE OPTIMIZATIONS
==========================

1. Database Indexes
   ✓ Composite primary keys on junction tables
   ✓ Foreign key indexes for relationships
   ✓ Covering indexes for common queries:
     - (organization_id, status) for org filtering
     - (device_id, created_at) for command lookup
   ✓ Unique constraints on unique_code, device_uuid

2. Query Optimization
   ✓ Eager loading via joinedload() for nested relationships
   ✓ Pagination with skip/limit pattern
   ✓ Only non-expired commands returned from query

3. Data Cleanup
   ✓ Speed tests: Keep last 100 per device (auto-delete older)
   ✓ Commands: Auto-expire after 7 days
   ✓ Logs: Indefinite retention (consider 30-day rolling window)
   ✓ Cascade deletes prevent orphaned records

4. Caching Potential
   ✓ Device settings (rotation, volume_enabled) in heartbeat response
   ✓ Activation code expiry can be checked client-side
   ✓ Content resolution results could be cached with TTL
   ✓ Tag-to-device mappings could be cached

INTEGRATION ARCHITECTURE
=========================

Device ↔ Content
├─ Direct assignment: Device → ContentAssignment → Content
├─ Tag assignment: Device → DeviceTag → Tag → ContentAssignment → Content
└─ Playlist assignment: Device → PlaylistAssignment → Playlist → PlaylistContent → Content

Device ↔ Organization
├─ organization_id FK (required field)
├─ All queries filtered by org
├─ Device creation validates org context
└─ Cross-org access returns 404

Device ↔ User
├─ created_by FK (who registered device)
├─ Activity logs track user actions
└─ User's org determines accessible devices

Device ↔ Monitoring
├─ last_seen for online/offline tracking
├─ device_logs for remote debugging
├─ device_speed_tests for network analysis
└─ device_commands for remote management

KNOWN LIMITATIONS
=================

1. Speed Test Implementation
   - Command queued but execution depends on viewer
   - No automatic scheduling (manual trigger only)
   - Consider adding cron job for periodic testing

2. Device Logs Retention
   - No log retention policy defined
   - Could grow unbounded with heavy usage
   - Recommendation: 30-day rolling window

3. IP Address Tracking
   - Device IP can change (DHCP, mobile networks)
   - No mechanism to track IP history
   - device_uuid available for permanent identification

4. Concurrent Command Handling
   - Device can have multiple pending commands
   - No priority system for execution order
   - Execution sequence depends on device polling
   - Consider adding priority field

5. Token Refresh Enforcement
   - Automatic refresh hint available
   - Device must manually call refresh endpoint
   - No forced refresh mechanism
